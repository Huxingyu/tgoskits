● 结论

  可以并行开始，而且建议并行——任务一的 1–4 步和任务二的 1–2
  步几乎没有真实依赖；但两条线在「实验输入冻结」和「vIRQ
  注入路径」上有两个明确的汇合点，如果不提前规划，任务二反而会把任务一的 A/B
  基线作废。下面按依赖、冲突、协同三方面详细分析。

  一、为什么大部分工作是正交的

  两个任务处在完全不同的层：

  - 任务一（步骤 1–4）：工作在 hypervisor 内部——分层 trace、synthetic vIRQ/timer
  workload、选改造点、写回归测试。改动集中在
  virtualization/axvm、arm_vgic、os/axvisor（从当前 git status
  看这条线已经开工：trace.rs、realtime_probe.rs、vgicr.rs 都有改动）。
  - 任务二（步骤 1–2）：工作在 Guest 侧和 VM 配置——给两个 Guest 分配独立
  virtio-net/MAC/IP/IRQ，验证互 ping 和双向 UDP，然后定义协议格式。主要产物是 VM
  配置、Linux 用户态程序和 Zephyr 应用，基本不碰 hypervisor 代码。

  技能栈也不同（Rust hypervisor 调优 vs. 网络协议/应用开发），如果有两个人或用
  subagent/worktree 分线，几乎零上下文冲突；即使一个人做，任务二的协议设计和
  Guest 应用编写也可以在任务一跑长时间测量的空档推进。

  另外从关键路径看，任务三只依赖任务二的协议，不依赖任务一——任务二越早打通
  ping/UDP，任务三的启动时间越早。所以任务二步骤 1 反而是全局最值得提前的动作。

  二、两个必须规划的汇合点

  汇合点 1：设备配置冻结必须在任务一 A/B 测量之前（关键）

  任务二步骤 1 会给两个 Guest 增加网卡、IRQ
  和后端，这改变了整个中断/设备拓扑。而任务一步骤 5
  要求"相同镜像、配置、绑定"下做 Native/A/B 对比，步骤 0 要求冻结设备/IRQ
  配置。如果先按无网卡配置跑完 A 基线，再让任务二加网卡，A/B
  对比的口径就变了，300/300 样本要重测。

  因此正确顺序是：任务二步骤 1（网卡/IRQ 配置落地并 smoke 通过）→ 步骤 0 冻结 
  manifest（含网络设备）→ 任务一步骤 5 的 A/B 测量。任务一的 1–4（trace
  分析、选点、写回归测试）不受此约束，可以立刻并行做。

  汇合点 2：virtio-net 中断走的正是任务一在改的路径

  virtio-net 的中断注入会经过 vgic/vIRQ
  队列——恰好是任务一的候选改造点。这带来两个影响：

  - 风险：任务二如果在任务一的 WIP
  分支（B）上调试网络，遇到丢中断/卡死时分不清是网络配置问题还是改造引入的
  bug。任务二应在未改造的 A 基线上打通，两条线用独立分支/worktree。
  - 协同：反过来，任务二的网络流量是任务一软件 vIRQ
  路径的真实压力源，可以作为步骤 5 stress 场景和步骤 6 长稳的负载之一。但注意
  plan 的固定决策：任务一的可控 workload 仍应是那个最小 synthetic
  vIRQ/timer，网络流量只作为附加压力，不作为测量口径本身。

  三、次要注意事项

  - 测量运行需要串行：开发可并行，但任务一的尾延迟测量对机器负载敏感，实际采样时
  段内不要同时跑任务二的压测/抓包，测量窗口在同一台机器上要互斥。
  - git 冲突面很小：两条线唯一共同触碰的大概是 VM
  配置文件（vCPU/设备定义），提前约定谁拥有该文件即可。
  - 隐藏风险提前暴露：如果 AxVisor 的 virtio-net 后端本身有问题，那就是
  hypervisor 层的活，会侵入任务一的代码区域——这也是"任务二步骤 1
  越早做越好"的又一个理由，早 smoke 早发现。

  建议的并行编排

  1. 立即并行：任务一步骤 1–4（trace → workload → 选点 →
  回归测试，在改造分支上）‖ 任务二步骤 1–2（网卡配置 + 互 ping/UDP +
  协议定义，在 A 基线上）。
  2. 同步点：任务二步骤 1 的设备配置合入基线 → 执行步骤 0 冻结（含网络设备的
  manifest）。
  3. 之后：任务一步骤 5–6 的 A/B 测量与长稳（测量窗口独占机器）‖ 任务二步骤 3–5
  的可靠性机制与故障注入测试（开发继续并行，压测错峰跑）。

  这样既不牺牲任务一 A/B
  数据的口径一致性，又把任务三的前置（任务二协议）尽早解锁。

  交叉点确认（按重要性排序）

  1. arm_vgic 的 GICR 修复是两个任务的共同硬依赖（最实质的交叉点）

  实验定位到的最终根因是：guest 初始化时写 GICR_ICENABLER0=0xffffffff
  被原样转发到物理 GICR，把 host 的 SGI0（IPI）和 PPI26（host
  timer）一起关掉了。修复（保留 SGI0/PPI25/PPI26 的 mask_host_private_interrupts
  ）已同步到本工作树——我核对过，virtualization/arm_vgic/src/v3/vgicr.rs 的本地
  diff 就是这个修复加回归测试。

  这对任务二不是"可能相关"，而是必然踩中：Linux guest 启动时同样会做 GICR
  私有中断的批量 disable，没有这个修复，双 Guest 网络场景下 host IPI/timer 会被
  Linux 的 GIC 初始化打死。所以这个修复必须先落到任务二依赖的公共基线上，而不是
  留在实验分支里。

  2. interrupt_mode 的选择把两个任务耦合在同一个配置轴上

  实验证明了一个此前不知道的事实：passthrough 模式下 host IPI 不会触发 EL2 VM 
  exit，host 侧的 drain→inject 注入路径根本走不通，队列在 64 容量处溢出；只有
  emulated GIC 才能形成 enqueue → notify → IPI → drain → inject → guest IRQ
  的闭环。任务一的 A/B 实验因此已冻结在 emulated GIC 上。

  任务二的 virtio-net 中断同样要靠 hypervisor 向 guest
  注入（SPI），大概率受同一约束。也就是说"任务二用什么
  interrupt_mode"不是任务二自己的自由选择——它要么跟任务一同样用
  emulated（顺带成为任务一路径的真实负载），要么如果 passthrough 下 virtio
  注入也不通，任务二会直接撞上任务一刚修完的那面墙。这一点应该在任务二第一步（互
  ping）时就显式验证。

  3. 任务一 B 改造的有界队列语义会直接作用于任务二的网络中断

  B 的改造是 per-vCPU 容量 64 的有界队列 + 定向唤醒，溢出返回
  ResourceUnavailable。实验里已经真实观察到溢出行为（passthrough 轮次
  queue_overflow=235）。任务二的网络流量是突发性的——如果虚拟网卡中断走同一条注入
  路径，突发包在 vCPU 未及时 drain
  时可能触发队列溢出，表现为丢中断。任务二的协议层有重传兜底，但这意味着：B 
  合入后，任务二的丢包/重传统计会混入任务一改造的队列行为，排查网络问题时必须知
  道这一层的存在。反过来这也是收益——任务二流量是 B 改造最好的真实压力测试（A
  的长稳已经在 18 万样本里丢了 6 个中断，B
  正在验证中；这正是任务二关心的可靠性维度）。

  4. 串口/trace 输出污染是两个任务共享的测量陷阱

  B2 那个 762ms 的假 outlier 根因是 dump_realtime_trace() 的约 6
  万条串口输出污染了最后一个样本，加 10ms grace 后消失。任务二的测试会有自己的日
  志输出（两侧日志、协议打印），如果和任务一的测量或 trace dump
  在同一串口上并发，会复现同类污染。这印证了我上一轮说的"测量窗口要互斥"，而且现
  在有了具体机制：不只是 CPU 负载干扰，串口本身就是共享瓶颈。

  对"能否并行"结论的修正

  方向不变（可以并行），但汇合点比原来更早、更具体：

  - 原来说"任务二的设备配置要赶在任务一 A/B 测量前冻结"——现在 A/B
  四轮短测已经跑完（均 300/300 有效，mean B 优 4.26%，p99 持平，p99.9/max B 优约
  11.8%），长稳进行中。这一版 A/B 用的是单 Zephyr guest 的实验配置（zephyr-soft
  -virq），不含网卡，所以任务二加网卡不会作废它——但如果之后要在"双 Guest +
  网络"的最终形态下重跑收益验证，那才需要含网卡的冻结配置。
  - 任务二现在就可以开始，且第一步应当做两件事：在含 GICR 
  修复的基线上配双网卡，并确认 virtio-net 中断在选定的 interrupt_mode
  下真的能送达两个 guest——这一步会立刻验证交叉点 2 是否成立。
  - 任务二的开发基线建议用 A 工作树这边（contest/openrace-2026 + 已同步的 GICR
  修复），等 B 长稳通过、改造合入后再让网络流量跑在 B 路径上做回归。

  一句话总结：任务一和任务二的交叉点不是抽象的"都用中断"，而是四个具体事实——GICR
  修复是共同前置、interrupt_mode 
  是共同约束、有界队列语义会改变网络中断的丢弃行为、串口是共享的测量污染源。前两
  个决定任务二怎么起步，后两个决定两边测试怎么互相解释数据。

  SGI0/PPI25/PPI26）与双 Guest passthrough 共存无副作用。

  #2 设计 QEMU 双 virtio-net 拓扑并写独立 QEMU 配置

  为什么单独建 QEMU 配置文件：任务一的 A/B 实验用的是共享的
  os/axvisor/configs/qemu/qemu-aarch64.toml，实验口径已冻结。任务二加网卡如果直
  接改这个文件，等于改了任务一的实验输入。所以新建
  scripts/test/net-dual-guest/qemu-aarch64-net.toml，--qemu-config
  指过来即可，两边互不干扰。

  拓扑设计的三个决策点：

  1. 设备形态：QEMU virt 机型的 virtio-mmio 传输。地址规律是固定的：slot n 位于
  0x0a000000 + n*0x200，对应 IRQ 16+n（SPI），即 GIC INTID = 48+n。两块 -device 
  virtio-net-device,netdev=... 按顺序占 slot，也就是 slot0 → 0x0a000000/INTID 
  48，slot1 → 0x0a000200/INTID 49。
  2. INTID 48 撞车问题：任务一的 synthetic workload 用的 software vIRQ vector
  恰好是 48。两个配置不会同时运行（不同 --vmconfigs），所以第一步互 ping
  阶段不冲突；但后面很可能要"网络流量作为任务一改造的真实压力源"（把两套东西合到
  一个运行形态里），届时同一个 INTID 一边是物理 SPI、一边是软件注入，trace
  和统计都会混淆。处理方式在这一步就定下来并写进文档：要么网卡避开 slot0（QEMU
  不能直接指定 slot，但可以用一个占位 virtio 设备把 slot0
  顶掉），要么约定合并实验时把 workload vector 改成别的（比如
  50+），推荐后者——改一个常量比操纵 slot 分配干净。
  3. 后端选型：三个候选——
    - -netdev hubport（两个 port 挂同一 hub0）：零主机配置，QEMU 内部转发，双
  Guest 互通最简单，缺点是性能一般、纯二层广播域；
    - tap + bridge：性能好、可上真实抓包工具，但要主机 root 配置，可复现性差；
    - socket：一般用于跨 QEMU 进程，这里是同一进程，没必要。

  推荐 hub 起步（互 ping 和协议阶段带宽要求极低），后续压测不够再换 tap。
  4. MAC 与抓包：固定 MAC（如 52:54:00:12:34:01 / :02），每个 netdev 挂 -object 
  filter-dump,id=...,netdev=...,file=xxx.pcap——这就是任务二 Gate
  要求"抓包可证明业务走 UDP/IP"的证据机制，从第一天就开着。

  产出：qemu-aarch64-net.toml + README 里一张 slot→MMIO 地址→INTID→所属 Guest
  的映射表。

  #3 按 Guest 分配 virtio-net 直通与互斥

  为什么：任务二的固定决策是"两张独立网卡各直通给一个 Guest"，隔离靠 AxVisor
  的设备分配实现，不是 Guest 自觉。Day3 的教训是设备集必须最小化（整树直通导致过
  193 条 DMA quarantine），所以网卡是"精确加一个节点"，不是放开一片。

  具体做什么：
  - Linux 配置的 passthrough_devices 加 ["/virtio_mmio@a000000"]（假设 slot0 归
  Linux），Zephyr 加 ["/virtio_mmio@a000200"]；如果 AxVisor 的 FDT
  过滤需要，配套补 passthrough_addresses。
  - 用 excluded_devices 确保对方的网卡节点从各自 Guest 的 FDT 里剔除——每个 Guest
  只能看见自己那块卡。

  一个必须提前核实的技术地雷（本项最重要的坑）：virtio 直通设备的 DMA 语义。QEMU
  的 virtio 后端按 Guest 写进 virtqueue 的物理地址直接读写"机器内存"。如果
  AxVisor 给 Guest RAM 建的是非恒等映射（GPA ≠ HPA），QEMU
  后端会写到错误的宿主物理地址——网卡要么不通，要么静默踩内存。Day3
  记录里恰好提到过 Linux 曾因 MAP_IDENTICAL/MAP_ALLOC
  的问题改过映射方式。所以这一步动手前要先确认当前 memory_regions = 
  [[0x8000_0000, 0x1000_0000, 0x7, 0]] 末位标志对应的映射模式：恒等映射则 virtio
  直通可行；非恒等则必须改回恒等（两个 Guest 的 RAM 区间 0x4000_0000 和 
  0x8000_0000 本就不重叠，恒等可行）或另想办法。这个结论不管是哪种，都写进
  README。

  完成判据：双 Guest 启动后，Linux dmesg 里出现 virtio_mmio probe 和 virtio_net
  网口（IRQ 号与映射表一致）；Zephyr/RTOS 侧只看到自己的设备；DMA quarantine
  仍为 0。

  #4 验证 virtio-net 中断在 passthrough/emulated 下的可达性

  为什么这是独立任务而不是"顺便就通了"：任务一实验刚刚用惨痛过程证明了
  interrupt_mode = "passthrough" 下 host IPI 不产生 VM exit，host
  侧注入路径完全走不通。网卡中断虽然是另一类（QEMU 注入的物理 SPI，不是 host
  软件注入），但双 Guest passthrough 下还有一个独立疑点：两个 Guest 
  共享同一个物理 GICD，各自初始化时都会写 SPI 的 enable/route/priority
  寄存器。UART/timer 能工作不代表 SPI 路由无冲突——PPI 是 per-CPU banked 的，SPI
  不是。Linux 把自己网卡的 SPI 路由到 pCPU1/2、Zephyr 路由到
  pCPU3，这两组写操作在无仲裁的物理 GICD 上是否互相破坏，只能实测。

  验证顺序：
  1. 先在 day3 沿用的 passthrough 模式下测：Linux 起网口后看 /proc/interrupts
  里网卡 IRQ 计数是否增长、收包是否触发；RTOS 侧看 ISR 是否进。
  2. 如果 passthrough 不可达或双 Guest 相互干扰，切 emulated
  GIC：照抄任务一实验已验证的 gppt-gicd/gppt-gicr
  写法（scripts/test/zephyr-soft-virq/axvisor-qemu-aarch64-emulated.toml），此时
  Guest 对 GICD/GICR 的写会被 vGIC 截获仲裁，GICR
  修复也已在本工作树，这条路在任务一实验里被打通过。

  为什么这个结论值钱：它同时回答了任务一的一个悬而未决的问题——虚拟设备中断和软件
  vIRQ 是否共用同一注入约束。无论结果是"passthrough 够用"还是"必须
  emulated"，都写成结论+证据日志记入 README，任务一后续做"网络流量压力下的
  A/B"时直接引用。

  完成判据：明确给出"哪种模式下、两个 Guest
  的网卡中断都稳定可达"的结论，有日志佐证。
