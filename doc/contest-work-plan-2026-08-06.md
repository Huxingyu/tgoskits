## 3. 主题选择

这里按公开比赛材料中的任务含义理解：

- **主题 1：实时性**——双 vCPU/CPU 绑定、周期任务、调度延迟或 jitter 测量，
  并进行 idle/stress/soak 对比。
- **主题 2：通信链路**——guest 之间的双向 IP 链路、版本化可靠协议、ACK、
  丢包/错误恢复等。

### 今天选择主题 1

理由：

1. 主题 1 可以先在现有 AxVisor/QEMU 代码和配置上建立最小纵向链路，不必先准备
   完整网络 guest、协议、rootfs 和物理板卡环境。
2. 我们可以保持实现完全原创，避免与已经合入的 #1770 的 AArch64 timer patch
   直接重叠。先做调度、绑核、测量和测试，后面再决定是否需要适配 timer 接口。
3. 今天的成果容易验收：有独立分支、有明确配置、有可重复测试、有原始数据和
   一份基线报告，而不是只有一堆尚未联调的代码。
4. 主题 2 不是不能做，而是更适合作为主题 1 的测量链路稳定后再接入；现在同时
   开始会扩大变量，增加调试和冲突成本。

## 4. 今天的具体任务

### 阶段 A：固定原创起点

1. 从本地 `dev` 的 `039ebf606` 创建独立分支，例如：

   ```text
   contest/task1-own
   ```

2. 记录起点 SHA，不合并远端 `origin/dev`，不引入其他选手 PR。
3. 保持本地 `dev` 不动；以后需要适配官方变化时，再创建单独的：

   ```text
   contest/task1-dev-integration
   ```

### 阶段 B：先做最小可运行链路

按以下顺序推进：

```text
vCPU/pCPU 绑定配置
    → 双 vCPU 启动
    → 周期任务
    → jitter/调度延迟采样
    → idle/stress 对比
    → 可重复测试与报告
```

今天不追求一次完成完整比赛方案，先明确以下最小接口和数据：

- 两个 vCPU 的目标 pCPU/亲和性配置；
- 周期任务的周期、运行次数和停止条件；
- 每次释放、开始执行、完成执行的时间戳；
- 最小值、平均值、最大值、p99 和丢样本数；
- idle 与 CPU stress 两种运行场景；
- 能够重复运行并产生带 commit SHA 的结果文件。

### 阶段 C：验证与留痕

- 为绑核/配置解析或调度测量逻辑添加确定性测试；
- 代码修改后运行 `cargo fmt`；
- 对受影响 crate 运行目标 clippy（优先使用 `cargo xtask clippy --package ...`）；
- 保存一次成功运行的命令、环境、commit SHA 和原始测量数据；
- 将失败原因与环境问题分开记录，不用“放宽阈值”代替修复实现。

追赶变化的 `dev` 修改实验结论。最终提交前，再把需要的上游变化放进
