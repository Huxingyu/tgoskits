  一、我对现状的判断

  已经拿稳的（约 12–17 分的证据基础）：Linux 2-vCPU + Zephyr 双 Guest 在 QEMU
  AArch64 passthrough 模式下可启动、0 DMA quarantine、有 Guest 内部证据（SMP: 2 
  processors、stress workers、300 样本周期采样）；Native/AxVisor
  初步基线；统计脚本的 deadline
  口径已修正并带回归测试；还有几个真实的正确性修复（FDT bootargs/PSCI、lower-EL
  IRQ 单次事务、vCPU slice 边界、vgicr 状态保留）。

  卡住的（决定剩下 ~13 
  分的部分）：三条实时性探索全部完成了"可复现的失败定位"但没有一条产出有效 A/B——

  1. passthrough 稳定但绕过了全部软件 vIRQ 链路（trace 只见
  vcpu_run/guest_exit）；
  2. 共享 pCPU 的 FIFO/RR 被 Guest run() 持有的 NoPreempt 阻塞（vcpu.rs:303 的
  with_current_cpu_set，这是架构约束不是 bug）；
  3. emulated 模式被 CNTV/PPI27 ownership/EOI 语义问题打死（30 秒 18,493

  4. 备选的 synthetic vIRQ smoke 又卡在 Zephyr 第二个 vCPU 的 CPU_ON
  启动参数（mpid=-1）上。

  核心矛盾一句话：评分要求"实质改造 + 改造前后最坏延迟改善"，但唯一稳定的
  workload 不经过你要改造的软件路径，而所有能经过软件路径的 workload
  都没跑起来。当前唯一的关键路径是：先让一个覆盖软件 vIRQ 链路的 workload 
  活过来，其他一切（trace、A/B、长稳）都排在它后面。文档里 next.md 的"先 trace

  二、我的思路

  1. 叙事框架：把矛盾变成"双模式"故事（对应 4 分分析项）

  不要把 passthrough 当成"绕过了改造对象"的尴尬，而是明确写成 hypervisor
  实时化的两条正统路线：

  - 静态分区路线（Jailhouse 式）：RTOS Guest 独占 pCPU + 中断/timer
  直通，hypervisor 退出热路径。现有 passthrough
  数据就是这条路线的验收证据（近原生尾延迟、隔离性、启动稳定性）。
  - 软件中断/定时器服务路线（KVM-RT 式）：emulated 模式下 queue → notify/IPI → 
  wake → drain → inject 是生产路径，改造对象和 A/B 都在这里。

  最终报告两条都交：passthrough 作为推荐部署形态（配隔离数据），软件路径改造配
  emulated workload 的 A/B。这与会议纪要里赵长收说的愿景（"AxVisor 本身就是个
  RTOS"）也是一致的。共享 pCPU + NoPreempt
  的失败定位本身就是高质量的关键路径分析材料——结论是"当前架构下 CPU
  分区是强制约束，宿主强制抢占 Guest 是后续方向"，写进报告而不是这一届去实现。

  2. 关键突破口：换一个更便宜的软件路径 workload（建议 2–3 天内定死）

  两条被阻塞的路线都比必要的复杂。我建议的首选方案：

  方案 A（首推）：宿主侧周期注入 + 单 vCPU Zephyr 消费者。 现在的 zephyr-virq
  设计是 Guest CPU0 发 SGI 给 CPU1，所以才需要 SMP、才撞上
  CPU_ON/mpid=-1。其实根本不需要 Guest 侧 producer：在 host 侧加一个
  feature-gate 的小注入器（约几十行），用 axvm/src/timer.rs 的 register_timer
  注册 10ms 周期回调，从 pCPU0 调 queue_interrupt(vm, vcpu0, 某个空闲 
  SPI)；Zephyr 单 vCPU 应用只做消费者（IRQ_CONNECT 该 SPI + IRQ handler 里读
  CNTVCT 存数组，结束后一次性 dump）。这样：

  - 一个 workload 同时覆盖 timer wheel（register→expire→callback）和 vIRQ 
  transport 全链（vcpus.rs:106 queue → notify → IPI → guest exit → drain →
  inject → Guest IRQ），正好是 next.md 里 T3–T11 的全部区间；
  - 完全绕开 CPU_ON/mpid=-1（那个问题另行归档——现象指向 Guest MMU-off 的 Device
  访存读不到 primary 的 cached 写，属于独立 bug，别让它挡路）；
  - Zephyr VM 用 emulated 中断模式（IPI 才能打出 guest
  exit，这正是要覆盖的模式），但把系统时钟关掉（SYS_CLOCK_EXISTS=n
  或等价配置，应用改忙等/WFI），从源头消掉 PPI27 风暴——不修 PPI27，是让 Guest
  根本不碰 CNTV；
  - host 侧 T0 和 Guest 侧 CNTVCT 同属一个系统计数器域（记录 CNTVOFF
  即可换算），端到端中断响应延迟可直接计算。

  方案 B（次选/并行探针）：CNTP 直编程 sampler。 arm_vgic/src/vtimer/ 里只有
  cntp_* 模拟（CNTP/PPI30），没有 CNTV——代码现状恰好支持"应用直接写
  CNTP_CVAL/CTL + IRQ_CONNECT(30)"的采样器，绕开 Zephyr 内核 timer
  驱动（它默认用 CNTV）。这条额外覆盖 vtimer sysreg 陷入路径，作为方案 A
  的补充消融。

  止损线：PPI27/CNTV 的正确语义修复（KVM arch-timer
  级别的工程量）保持冻结；若方案 A/B
  三天内都起不来（我认为概率很低，因为不再依赖任何 Guest SMP/timer
  驱动行为），退回"host 内自注入微基准 + passthrough 演示"并如实写限制。

  3. B 改造点预判：三个有代码依据的候选（测量后只选一个）

  按我读到的代码，A 阶段 trace 大概率会把矛头指向这几处，提前把设计想清楚：

  1. per-vCPU 有界无分配中断队列 + 
  定向唤醒（我预判的第一候选）。现状是两层几乎同构的 SpinNoIrq<BTreeMap<usize, 
  Vec<...>>>（vm/mod.rs:192 和 runtime/queue.rs:36）：VM 级全局自旋锁、锁内 Vec
  push 可能触发分配、drain 每轮再分配一个 Vec；而且 queue_interrupt 之后是
  notify_all()（vcpus.rs:119-122）——每来一个 Zephyr 中断就把该 VM 所有 vCPU 
  任务全部惊群唤醒。改成 per-vCPU
  固定容量环形队列（预分配、有界、溢出显式计数）+ 只 notify 目标 vCPU
  任务，是教科书级的实时改造：有界内存、有界临界区、O(1)、消除跨 vCPU
  干扰。确定性回归测试好写（容量/顺序/并发入队/溢出语义），trace 上对应 T3–T4 和
  T5–T7 区间，收益可直接归因。
  2. timer wheel 全局锁拆 per-CPU。timer.rs:112 是单个全局
  SpinNoIrq<TimerWheels>，所有 CPU 的 register/cancel/expire 串行化——pCPU0 上
  Linux 相关的 timer 操作会直接顶到 pCPU3 的中断响应尾部。拆成真 per-CPU
  存储后跨核竞争归零，单元测试现成（该文件已有不错的测试基建）。
  3. （fallback，passthrough 就能测）RTOS pCPU 的宿主干扰隔离。若软件路径
  workload 最终还是起不来，用 ring trace 数一数采样期间 pCPU3 上的宿主 IRQ/timer
  到达次数，把宿主 tick/IRQ affinity 从 RTOS 核上挪走（nohz_full/isolcpus
  思路）——这是现有稳定 workload 能测出 A/B 的改造，Day5 那些 1.3ms 的 max
  尾巴需要先归因，这一步反正要做。

  注意 8 分"实质改造"其实已部分入账（lower-EL 单次 IRQ 事务修复带回归测试、slice
  边界），缺的是 5 分"改造前后数据"——所以 B 的选择标准是可被 workload 
  覆盖且尾部可归因，而不是越大越好。

  4. 测量基建的两个必修小项

  - trace_runtime_event（vcpus.rs:29-43）现在是 debug! 逐条串口打印——正是
  next.md 自己禁止的观测方式。A 阶段测量前必须换成计划中的 per-CPU 固定容量 ring
  buffer（批量导出 + off/on 校准），否则观测本身就把尾延迟改了。
  - 串口交织丢行问题（Day5 手工重建 4 行、Day6 缺 6 行）不可持续：给 CSV

  dump。一次小改，省掉每轮人肉重建，也消除"改造后数据不完整"这类审计瑕疵。

  ---
  路 1：passthrough + runtime trace —— 不是失败，是架构必然

  机理（代码级）：arm_vcpu/src/vcpu.rs:258-266——只有 !passthrough_interrupt
  时才设置 HCR_EL2.IMO/FMO。passthrough 模式下 IMO=0，物理 IRQ 到达 PE 后直接送
  EL1 Guest，根本不进 EL2；同时 vcpu.rs:241-244 把 CNTHCTL_EL2.EL1PCEN/EL1PCTEN
  置位，Guest 的 timer 访问也不
  trap。于是中断和定时器在"GIC→Guest"硬件层闭环，queue_interrupt → notify → IPI 
  → drain → inject（runtime/vcpus.rs:106-180）一行都不会执行，稳态下 Guest
  除了偶发 MMIO/sysreg/HVC 几乎不退出。trace 只见少量 vcpu_run/guest_exit
  是必然结果，不是 workload 选错。

  判断：不可"解决"，因为没有故障——这条路上软件层不存在。它的价值是静态分区路线的
  验收证据（启动、隔离、近原生尾延迟）。v13/v17 把它定为控制组是对的，维持。

  路 2：共享 pCPU + FIFO/RR —— 两个架构属性叠加，卡点不在调度策略

  机理：两层叠加。第一层，vcpu.rs:303 的 with_current_cpu_set 全程持
  NoPreempt——这是 per-CPU 状态（CURRENT_VCPU 发布、pCPU
  pin）正确性的前提，抢占点只存在于 guest exit 之后的 slice
  边界（architecture/ops.rs:171-180 最近已把 handled exit
  做成显式边界）。第二层，passthrough 下（路 1 机理）几乎没有 exit → slice
  无界。而且更狠的是：IMO=0 时宿主在这颗 pCPU 上连自己的 tick 中断都收不到（物理
  IRQ 全部路由 EL1），所以 RR 依赖的时钟抢占根本无法发生——FIFO 饿死 Zephyr、RR
  退化成 FIFO 无样本，全部自洽。

  可解吗：可解，但等于设计一个新机制，不是调参数。两个真实方向：
  1. 给宿主留 FIQ 后门——宿主 tick 放 GIC Group 0/FIQ，保持 FMO=1、IMO=0，Guest
  中断直通、宿主用 FIQ 强制取回 CPU（分区 hypervisor 的经典做法）；
  2. 共享核场景改用 emulated 模式（IMO=1），exit 边界天然存在。

  判断：本届不做。主线部署形态就是 RTOS vCPU 独占
  pCPU，这个失败定位本身是高质量的"关键路径分析"材料——把"为什么当前架构下 vCPU
  必须静态分区、宿主为何无法抢占"写实，比硬改抢占机制值钱且零风险。

  路 3：emulated timer / PPI27 风暴 —— 真功能缺口，可解，路线成熟

  机理（现在能完整拼出）：emulated 模式 IMO=1（宿主接管全部 IRQ），但
  CNTHCTL_EL2 只能 trap CNTP（物理 timer）——arm_vgic/src/vtimer/ 目录下也只有
  cntp_* 系列模拟，CNTV 的模拟和所有权管理根本不存在。而 Zephyr arm64 内核 timer
  默认用 CNTV：Guest 直接编程真实 CNTV 硬件 → 到期后 PPI27 作为物理中断进 EL2 →
  宿主 IRQ 表里没有 27 的 action → "unhandled"。CNTV_CTL.ISTATUS
  是电平语义，Guest 收不到注入就不会重编程/屏蔽，条件持续成立 → EOI
  完立刻重新触发 → 风暴（18,493 次/30s，约 616 次/秒，量级正好跟每次 warn
  串口打印的耗时吻合，实际硬件重入率只会更高）。临时"直接排队注入
  27"失败的原因也清楚：注入了软件 vIRQ 却没接管硬件状态——不 mask CNTV、LR 没带
  HW bit 链接物理 27、EOI 生命周期断裂。撤销是正确决定。

  可解吗：可解，且是三条里含金量最高的。两条路线：
  - (a) KVM 式 CNTV 所有权管理（正解）：宿主注册 PPI27 handler；到期时从 EL2 写
  CNTV_CTL.IMASK 屏蔽源头，用 ICH_LR(HW=1, pINTID=27) 注入 vIRQ27，Guest EOI
  时硬件自动 deactivate 物理中断；vCPU 切换时保存/恢复 CNTV_CVAL/CTL。估 3–5
  个专注人日，难点全在电平/EOI/迁移语义（KVM arch_timer
  踩过的坑要重走），但可以写"单次 fire→单次注入→EOI→不重入"的确定性回归。
  - (b) FEAT_ECV 的 EL1TVT trap CNTV，复用现有 cntp 模拟框架：QEMU -cpu max
  可用，但 RK3568/RK3588（A55/A76，ARMv8.2）没有 ECV，上板即死——只能当 QEMU
  阶段过渡。

  B：它恰好就是任务一想要的"软件 timer 关键路径实质改造"，如果 A 阶段测量指向

  CNTP/PPI30（模拟已存在）或宿主侧注入。

  路 4：synthetic vIRQ 的 mpid=-1 —— 真 bug，且 cache 假设可以直接划掉

  先说排除掉的：

  - "vCPU1 抢跑在 primary 写入之前"不成立——VM 启动只拉主 vCPU

  - MPIDR 数值链没有错位——生成 FDT 只保留 cpu@{phys_id}（boot/fdt/core/create.rs
  的 need_cpu_node），VMPIDR=phys_cpu_id（arch/aarch64/vm.rs:80、arm_vcpu/vcpu.
  rs:271-276），CPU_ON 按 phys_id 解析（cpu_up.rs:22-26）。smoke 配置

  - cache 假设直接出局——宿主 x86_64、QEMU TCG，TCG 不建模 
  cache，访存天然全局一致。"cache sync 修复无效"不是修复没写对，而是这个环境里
  cache 根本不可能是根因。realtime-directions 表里"Guest RAM
  可见性"一栏的缓存方向可以停了。

  于是剩下的根因空间非常窄：primary 的写在 TCG 下立即全局可见，vCPU1

  1. （首选）vCPU1 首次进入时 stage-2 未生效或 VTTBR/HCR.VM 状态不对，它把 GPA

  2. （次选）vCPU1 的入口 PC/SCTLR 不是干净的冷复位语义，实际走的不是预期 reset
  序列，观测到的 -1 是探针地址换算（链接 VA vs GPA vs HPA）误读。
  3. （再次）目标 pCPU 的 per-CPU EL2
  状态（hardware_enable/VTCR）与主核不一致；vcpus.rs:434-461 的 cpumask fallback
  会静默换核并只打 warn，smoke 日志值得回查这条 warn。

  2. "架构属性"是什么意思？改了能提高实时性吗？

  架构属性 = 系统按设计意图运行所必然表现出的行为，不是缺陷。 它的反面是 bug（路
  4：设计意图是 secondary 读到正确的 boot 参数，实际读到
  -1——行为偏离了意图）。路 1 和路 2
  的"失败"，是系统精确地做了设计要它做的事，只是这个设计和你的实验目标冲突了。改
  架构属性不是"修复"，而是换一组权衡——所以要分别回答"改了有没有实时收益"：

  路 1（passthrough 绕过软件层）：改了只会更差，别改。
  这个属性本身就是一种实时优化——IMO=0 让中断从 GIC 直达 Guest，是物理上可能的最
  低延迟路径，接近裸机。它付出的代价不是延迟，而是灵活性：hypervisor
  失去了拦截、排序、优先级仲裁中断的能力，也没法让多个 vCPU
  共享这颗核。你如果"改掉"它（让中断绕回软件层），延迟只会变高。所以对独占核的
  RTOS Guest，正确做法是保持原样，把它作为"分区式实时"的证据；它唯一"不能提供"的
  ，是下面路 2 那种能力。

  路 2（NoPreempt + 宿主收不回 
  CPU）：改了确实能提高实时性——但只在共享核场景，而且贵。
  先看这个属性保护什么：NoPreempt 保证 Guest 运行期间 per-CPU 状态（当前 vCPU
  发布、pCPU 绑定）不被迁移破坏，这是正确性不变量；IMO=0
  则让宿主在这颗核上交出了全部中断，连自己的 tick
  都收不到。合起来的必然结果就是"宿主无法抢占正在运行的 Guest"。

  改造它意味着建立一个新能力：宿主用有界延迟收回 CPU 
  的手段。具体形态大概是——宿主 tick 挂到 GIC Group 0/FIQ（FMO=1、IMO=0，Guest 的
  IRQ 继续直通，宿主保留 FIQ 后门），或共享核统一用 emulated
  模式制造天然退出点；再配上带优先级和唤醒抢占的 vCPU
  调度。做成之后你得到的实时收益是真实且可测的：共享 pCPU 上，RTOS vCPU 
  抢占非实时 vCPU 的延迟有界——这正是 Xen RTDS、KVM-RT 这类"hypervisor
  实时调度"的核心内容，也是会议纪要里"AxVisor 本身就是个 RTOS"愿景的必经之路。

  但两个现实约束：其一，收益只在共享核场景可测——你们主线是 Zephyr 独占
  pCPU3，没有竞争，这个改造在主线上测不出任何差异，要演示它就得专门搭共享核实验
  ；其二，它动的是正确性不变量本身（要么重新设计 per-CPU
  状态的迁移安全性，要么在 FIQ 里做受限操作），是四个方向里工程风险最高的。这就
  是我说"本届不做、写进分析"的原因：不是不能改、改了没用，而是投入产出比在 12 
  天窗口里排不上。

  ---
  一句话总结

  实时性改造其实分三类：修偏差（路 4 的
  bug——恢复设计意图，不产生延迟收益）、补能力（路
  3——让路径从不可用变可用，是实质改造但不是 A/B 改善）、换权衡（路 2

  Phase 2：解除屏蔽的时机 + 注入去重（1 天，语义核心）

  fire 一次 → handler 再 mask + 入队，gic.rs 的 pending/active
